# schemas/

One JSON Schema (draft 2020-12) per record type, `<name>.schema.json`, and one example per schema in
`examples/<name>.example.{yaml,json}`. `tests/test_schemas.py` validates every example, the shipped data files
that name a schema, the repository's `<tool>.example.toml` and every record of the demo instance in `examples/demo/`.
The demo is the contract the commands are tested on: change a schema, and the demo and its example follow in the
same change.

## Conventions

- **The first key of every record is `schema`**: `"<tool>/<name>/<version>"`, for example `easel/recipe/1`.
  The schema file pins it with `const`.
- **`$id`** is `urn:<tool>:<name>:<version>`, for example `urn:easel:recipe:1`; the file name is `<name>.schema.json`.
- **A format change is a version bump** (`.../2`) plus a reader for the old version. Schemas are frozen once
  released; a new optional field is still a bump when a reader would mis-read old files without it.
- **Event logs** (`*.jsonl`) carry on every line `schema`, `at` (ISO time), `v` (the line format's version, the
  same number as the end of `schema`) and `source` (who or what the line's content comes from: `operator`, the
  second source `assistant`, or a tool). On image lines `source` is an object saying where the image came from.
  Readers reduce the latest line per key and skip a torn last line.
- **Ids**: images `img-<sha256[:12]>`, resources `<sha256[:16]>`, runs `run-YYYYMMDD-<slug>`, recipes
  `rcp-YYYYMMDD-NNN`, jobs `job-YYYYMMDD-NNN`, decisions `dec-NNNN`, snapshots `<slug>/<version>`. Records exported
  from an older store keep that store's id in `legacy_id`.
- **Paths** in records are relative (forward slashes, no drive, no leading slash, no `..`) to the root the record
  names, or start with a config token such as `{images_root}` or `{models_root}`. Absolute paths live only in an
  instance's TOML.
- **Annotations** `x-file` (where the record lives), `x-owner` (person, tool or maintainers) and `x-kind` (record
  or event-line) are read by the formats doc generator; validators ignore them.
- Keys starting with `_` are comments where a schema allows them (the subject spec).
- Examples and the demo use the synthetic subject `demo_robot` (trigger `dmrbt`), ids and dates in 2030, and
  synthetic model ids from 9000000000 up. Their media are generated by `tests/fixtures/make_fixtures.py` into the
  gitignored `tests/fixtures/_gen/`; nothing binary is committed.
